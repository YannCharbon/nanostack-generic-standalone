# Wi-SUN FAN 1.1 LFN in the upper layers: one LFN under the border router

GS8 stages 3–5 (root repo: `documents/pre-study/investigation/LFN_FAN11_Study.md` §5, items U2–U13, U15). The MAC and FHSS mechanics are in `LFN_MAC.md`. This note describes what the LLC, the LFN bootstrap and the border router do, the settings, the sources each rule comes from, the deviations from Silicon Labs' implementation, and the tests.

Tags as in `LFN_MAC.md`: **[S]** a public source (`LFN_MAC.md` §7: the Arm codecs, Wireshark's dissector, `wisun-br-linux` and its `HIF.md`, RFC 8505; for LGTK, §8); **[M]** observed on Silicon Labs' LFN (root repo, `HW5_BlackBox_Phase1_Results.md`, item numbers); **[I]** our choice or inference, to check in black-box phase 2.

## 1. Summary

- **FFN routers as parents** (stage 5, §9): a FAN 1.1 router with `ws_management_lfn_parent_set()` parents LFNs once it is operational and holds an LGTK, which it gets from the border router by EAPOL; LFNs choose among the parents that answer their discovery (LND slots); the router relays their EAPOL and DHCPv6 and registers their addresses with the border router (RPL DAO).
- **Run-time only.** An interface is an LFN when the application starts it with `NET_6LOWPAN_HOST` (`arm_nwk_interface_configure_6lowpan_bootstrap_set()`); the router library contains the LFN code (`HAVE_WS_HOST`). A border router parents LFNs after `ws_management_lfn_parent_set(id, true)`, which needs FAN 1.1. With neither, nothing changes: FAN 1.0 `dag_simple` logs are byte-identical (§7).
- **Join** (`ws_bootstrap_lfn.c`): LPAS sweeps → LPA in the LFN's next listen window → EAPOL with the parent as authenticator (shorter listen interval meanwhile) → LPCS → LPC → DHCPv6 through the parent → address registration (NS with ARO) to the parent. No RPL, no MPL forwarding; a default route through the parent.
- **Parent side** (`ws_lfn_parent.c`, border router): LPAS → the LFN child and a unicast LPA with an LTO-IE; LPCS → LPC; frames to an LFN child wait for its listen window (FHSS parent role, `LFN_MAC.md` §4); an LPC to every LFN child every sync period; a MAC-unicast copy of each `ff02::1` multicast to every LFN child, and of each packet of a group to the LFN children that registered it (RFC 9685, §4).
- **Multicast subscriptions** (RFC 9685): the LFN registers the groups it joins (`SOCKET_IPV6_JOIN_GROUP`) with its parent, an EARO with P = 1 and the lifetime and refresh of its address registration; its parent copies the group's packets to it, also under a router (§4, §9).
- **Better parent while attached** (§9): a background discovery every few hours (6 h; 1 h while the parent's link is weak) moves the LFN to a clearly better parent, with hysteresis, without EAPOL, and releases the old one.
- **LGTK** (§8): the LFN authenticates with a node role KDE and gets LFN group keys (LGTKs, MAC key indexes 5–7) instead of GTKs; the border router keeps three LGTKs with their own lifetime, rotates them, announces each change with the LFN version and LGTK hash in an LPC to every LFN child, and activates a new LGTK only once its LFNs can have fetched it; the LFN fetches a new LGTK `lgtk_max_mismatch_s` after it sees its hash. FFNs keep their GTKs.
- **LFN broadcast schedule and sync** (stage 4, §4.1 and `LFN_MAC.md` §2.2–2.3): while it has an LFN child, the border router sends a sync frame in the LFN broadcast slot of every sync period (an LTS, or a broadcast LPC after the schedule starts and after each LGTK event); the LFN listens in the parent's broadcast slots, syncs from every frame with an LBT-IE, keeps its own unicast slots in the parent's time base and widens its windows for clock drift.
- **Parent maintenance**: the LFN declares its parent lost after 1.5 × `maintain_parent_time` sync periods with no sync frame from it (LTS, LPC) [M items 34, 46], then rediscovers and rejoins without EAPOL [M item 47].
- **Checked** in virtual time with `wsbrd-inproc` and `wsnode-inproc` (emulator `sim_utils/vtime/test_lfn_join.sh`, §7).

## 2. Frames and IEs (LLC, `ws_llc_data_service.c`)

| Frame | Sent by | Header IEs | Payload IEs | Security | Source |
| --- | --- | --- | --- | --- | --- |
| LPAS (type 10) | LFN, asynchronous on every channel | LUTT, NR (role LFN, interval range), LUS (tag 1), LND (with a random Discovery First Slot) | LCP (tag 1: the LFN's unicast schedule), NETNAME | none | [S] codecs, `wsbrd` `ws_mngt.c` (needs the LCP-IE of the LUS-IE's tag); [M] items 1–4 |
| LPA (9) | parent, unicast | UTT, BT, NR, FLUS (dwell, tag 0), PANID, LBS (tag 0), LTO, LBT | LCP (tag 0: the parent's unicast schedule), BS, PAN, NETNAME | none | [S] `ws_mngt.c` IE list, [M] item 5 |
| LPCS (12) | LFN, unicast | LUTT, LUS (tag 255) | NETNAME | active LGTK (ours); none (Silicon Labs' LFN) | [S] `wsbrd` needs NETNAME; [M] item 13 |
| LPC (11) | parent, unicast (answer to an LPCS) or broadcast in an LFN broadcast slot | UTT, BT, LBS, LBT | LFNVER, LGTKHASH | active LGTK | [M] items 14, 48, §5.2 |
| LTS (13) | parent, broadcast in an LFN broadcast slot | UTT, BT, LBT | none | active LGTK | [M] items 24, §5.2 [I: IE set] |
| Data, EAPOL | LFN | LUTT, LUS (tag 255: "current", instead of UTT, BT) | — | data: active LGTK; EAPOL: none | [S], [M] |
| Enh-ACK | LFN | LUTT (frame type 5), RSL | — | as the frame acknowledged | [M] (Silicon Labs' LFN) |

- **Frame type** is 8 bits in `asynch_request_t` and 4 bits in an LLC message (types up to 13).
- **Broadcast sync frames** go through `ws_llc_asynch_request()` with `lfn_broadcast` set: the MAC holds them for the next LFN broadcast slot (`LfnBroadcast`, `LFN_MAC.md` §2.2). An LTS has header IEs only; the MAC now accepts such frames (it dropped a frame with IEs and no payload) and the LLC passes it to the bootstrap without payload IEs.
- **Receiving**: a frame with a LUTT-IE and no UTT-IE is accepted (FAN 1.1 only); its LUTT/LUS fill the sender's `lfn_uc_timing_info` (`ws_llc_lfn_timing_update()`), instead of the UTT update. LPA, LPC, LPAS and LPCS go to the bootstrap's asynchronous handler.
- **Unicast management frames** go through `ws_llc_asynch_request()` with `unicast` set: acknowledged, no channel list, so the MAC holds a frame to an LFN for its window. An LTO-IE that the LFN acknowledges is applied to the parent's view of its schedule on the ACK (`ns_fhss_ws_lfn_neighbor_lto()`).
- **LBS-IE** now has its sync-period byte (7 bytes, as Wireshark's dissector and `wisun-br-linux`; the Arm codec had 6). Nothing called the old one.
- **Channel plans (black-box phases 2–3).** An LFN gives its unicast schedule once, in an LCP-IE of its LPAS (tag 1, the LUS-IE's tag), and "current" (tag 255) in its LUS-IEs afterwards; a parent gives its unicast schedule as FLUS-IE (dwell interval, tag 0) + LCP-IE (tag 0) in its LPA, no US-IE [S: `wsbrd` `ws_mngt.c`, `ws_llc.c`; M: Silicon Labs' LFN and both parents]. Readers take the LCP-IE of the tag given, or a US-IE (our nodes before this change). With a FAN 1.1 channel plan ID (`ws_management_domain_configuration_set()`, PHY mode ID + channel plan ID) the US, BS and LCP IEs use channel plan 2 (regulatory domain and channel plan ID), which `wsbrd` requires in an LCP-IE; FAN 1.0 configurations (no plan ID) are unchanged. `wisun-br-linux` reads the LCP-IE of a non-255 LUS tag in data, EAPOL and LPCS frames from the header IEs (where it never is), so an LFN must send tag 255 there.
- **Payload IE IDs of the LPC**: LFN Version 0x40 and LGTK Hash 0x41 (short nested IEs) [S: `wisun-br-linux` `ws.h`, Wireshark's dissector; M: both Silicon Labs parents]. The Arm codec used 9 and 10 (IDs of the LBATS and JM IEs today), so our LFN ignored a Silicon Labs parent's LFN version and LGTK hash and never fetched a new LGTK.
- **LBC-IE and POM-IE** (phase B7) [S: Wireshark's dissector (`WISUN_SUBID_LBC` 0xC0: interval 3 bytes, sync period 1 byte; `WISUN_PIE_SUBID_POM`); `wisun-br-linux` v2.10.3 `ws_mngt.c`, `ws_llc.c`, `ws_ie.c`, read for the rules]. The LBC-IE (LFN Broadcast Configuration, header IE) carries the PAN-wide LFN broadcast interval and sync period; `wsbrd` puts it in its PAN configurations while LFNs are enabled, and its router (`wsrd`) does not read it yet. Our border router now sends it in its PAN configurations when it parents LFNs; a FAN 1.1 router reads it, takes the values for its own LFN broadcast schedule (restarting that schedule if the interval changed) and repeats the IE in its PAN configurations. So all parents use the border router's LFN broadcast interval and sync period, and an LFN that changes parent keeps them. Checked: `test_lfn_join.sh MESH=1` with the router configured for 20 s × 3 (`ROUTER_EXTRA`), 3 seeds: the router took 10 s × 5 from the LBC-IE 23 s after start and the LFN under it saw a 50 s sync period; every check passes. The POM-IE (PHY Operating Modes) lists the PHY modes of a node for mode switch; `wsbrd` sends it in PAN advertisements, EAPOL and data frames only when several PHY modes are configured, and nothing LFN-specific depends on it. Our network runs one PHY mode, so neither our LFN nor our parents send or need it; the Arm stack's older PHY capability IE (`ws_wp_nested_pcap_*`) is not the POM-IE. Not implemented: mode switch.
- **Kept deviations [I]**: no Silicon Labs vendor IE (LFN session ID, `VH 1a 02 xx`) in our LPC and LTS; our LPA, LPC and LPCS request an acknowledgement (Silicon Labs' are unacknowledged, with the sequence number suppressed); our LPCS is secured; no JM-IE in our LPA. Results with Silicon Labs' stack: root repo, `LFN_BlackBox_Phase2_3_Results.md`.

## 3. The LFN (`ws_bootstrap_lfn.c`)

| State | What it does | Source |
| --- | --- | --- |
| Discovery (`ER_ACTIVE_SCAN`) | FHSS: own unicast channel function, no broadcast schedule; listen schedule at the proposed interval (started without a PAN: `ns_fhss_ws_lfn_listen_start()`); receiver off outside windows. An LPAS sweep every `lpas_interval_s` until an LPA comes | [M] items 1, 8 |
| LPA | Network name checked; PAN ID from PANID-IE; the parent becomes a neighbour (UTT, FLUS + LCP or US, BS, BT); its broadcast schedule is given to the FHSS (uplinks avoid its dwell); LTO-IE applied (offset, adjusted interval within the NR range); LBS gives the sync period | [M] items 5–6 |
| Authentication (`ER_PANA_AUTH`) | Listen interval `eapol_listen_interval_ms` (1 250 ms), EAPOL with the parent as target (the existing supplicant); skipped on a rejoin with valid keys | [M] items 10, 36, 47 |
| Configuration (`ER_SCAN`) | Still at `eapol_listen_interval_ms` (also on a rejoin with valid keys); LPCS, repeated every `lpcs_retry_intervals` listen intervals until an LPC. The agreed interval comes back with the first address registration, whose NS carries it (LUS-IE): before, the LPC and the DHCPv6 reply each waited one agreed interval (Eco: 300 s each; with a 4 h interval the LFN was operational after 4 h) | [M] items 13–15; [I] |
| Operation | Default route through the parent; DHCPv6 Solicit to the parent's link-local address (no prefix hint); on the reply, NS with ARO (lifetime `registration_lifetime_min`) to the parent, then one NS with an EARO (P = 1) per multicast group; re-registration of both at 92 % of the lifetime | [M] items 16–19, 52; RFC 8505; RFC 9685 |
| Sync | Every frame from the parent with an LBT-IE (LPA, LPC, LTS) syncs the FHSS to its LFN broadcast schedule (`ns_fhss_ws_lfn_bc_sync()`, with the LBS-IE values kept from the LPA or an LPC and the parent's broadcast channel function) | [M] items 21–25, §5.2 |
| Maintenance | A sync frame from the parent keeps it; lost after 1.5 × `maintain_parent_time` × sync period without one → broadcast windows stopped, discovery, keys kept. Other secured frames keep the parent's neighbour entry only. A search while keeping the parent when it goes silent or uplinks fail, and background checks for a better parent (§9) | [M] items 34, 46, 47; [I] |

- **Group key before the first LPC**: the LFN sends its LPCS with the lowest LGTK installed by the 4-way handshake (key index 5–7); every LPC's key index then sets the active one (as an FFN learns its GTK from a PAN configuration), after the LPC's LGTK hash has been applied (§8).
- **Neighbours**: the LFN keeps only its parent; its entry is refreshed by every frame from it, and does not expire while it is the parent (parent maintenance decides; the usual 2 200 s lifetime again once dropped). Before, with a listen interval or sync period beyond 2 200 s the entry expired and every uplink was refused ("Adaptation Layer Data req fail") until the next frame from the parent [I].
- **Duplicates**: a unicast frame is dropped as a duplicate when it has the sequence number of the last one accepted from that neighbour, the same payload IEs (Fletcher checksum) and comes within 5 s of it, or within 5 s + 2 listen intervals on an LFN (a parent's retry comes in the next window). Before, the 5 s were measured from the neighbour's UTT reference, which the LFN moves forward (the parent's FFN schedule, re-anchored for the 32-bit clock), and the payload was not compared: a new frame whose 8-bit sequence number matched the previous one was dropped (the NA of a 4 h interval run), and a retry one Test-profile interval (5 s) later was delivered twice (`better_move` seed 3) [I].
- **Multicast subscriptions** [S: RFC 9685 §5 (subscription by an EARO with P = 1, Target = the group); RFC 8505 §4.1 (EARO); M: Silicon Labs' LFN registers `ff03::1` this way, item 19]: the LFN registers the interface's groups of realm-local scope or wider, except `ff03::fc` (the MPL domain) and the all-routers groups (an LFN is no router). The application joins a group with the socket option `SOCKET_IPV6_JOIN_GROUP` (interface given: the group has no route before the join); the stack also has `ff03::1`. Each registration is an NS from the LFN's link-local address to the parent's, Target the group, an EARO with T set, P = 1, a new TID [I] and the lifetime `registration_lifetime_min`, and an SLLAO (`icmpv6_build_ns_earo_mc()`). They go with the address registration and its refresh at 92 % of the lifetime (`ws_bootstrap_lfn_address_register()`); a group joined later is registered at once, a group left is deregistered with lifetime 0 (hook in `mld_start_listening()` / `mld_stop_listening()`, `ws_bootstrap_lfn_group_change()`).

## 4. The border router as parent (`ws_lfn_parent.c`)

- **LPAS**: needs NETNAME, NR (role LFN), LUS, LUTT and the LCP-IE of the LUS-IE's tag (or a US-IE). The LFN becomes a neighbour (an "LFN child": `lfn_uc_timing_info` set, `ffd_device` false, lifetime 2 × the registration lifetime, refreshed by its frames; no NUD or ETX probing). One LPA per discovery: no new LPA is queued while an earlier one to the same LFN still waits for a window (`ws_llc_lfn_lpa_pending()`; the only rule of `wisun-br-linux` v2.10.3 `ws_mngt_lpas_analyze()` [S]), and after an LPA the LFN acknowledged, its LPAS are ignored until the end of that LPA's discovery window (LND-IE slots × slot time, + 1 s): the other LPAS of the same sweeps. A lost or unacknowledged LPA starts no hold-off. Before, a hold-off of 2 proposed intervals started before the LPA was sent, even when it was then dropped: under the Eco profile (300 s) a lost LPA delayed the join by about 10 min (601 s without an answer). Now the LFN's next sweep, 10 s later, is answered: Eco settings, one LFN under the border router with its first LPA dropped (`ws_test_lfn_lpa_drop()`, emulator `test_lfn_lpa_drop = 1`), 3 seeds: the second or third sweep answered, operational at 630–930 s against 618–620 s with no drop (the spread is the LTO phase of the new LPA: the LPC waits for the LFN's 300 s slot). Otherwise a second LTO-IE would move the LFN's schedule in our view only: the LFN ignores an LPA once it has a parent, but the border router applies the LTO-IE of each acknowledged LPA. (Found during the LGTK work: an LPA from the first sweep, still queued, was sent after the one the LFN took, and the border router then missed the LFN's windows until its next uplink, about 340 s.)
- **LTO-IE** (`lfn_lto`, default on) [S: the rule described in `wisun-br-linux` `ws_neigh.c`, our arithmetic]: the proposed interval snapped to a multiple (above) or a divisor (below) of the LFN broadcast interval within the LFN's NR range (6 000 ms → 5 000 ms with 10 s, as observed [M item 6]); the offset a random multiple of 300 ms in [300, min(interval, broadcast interval) − 300] ms.
- **LPCS**: from a known LFN → LPC. Secured (ours) or unsecured with the network name (Silicon Labs' LFN); an unsecured one does not make the LFN a trusted neighbour (its secured frames do).
- **LPA in an LND slot** (`LFN_MAC.md` §2.4): a random slot *k* of the LFN's discovery window, a quarter into it, on the LFN's channel of slot number `discovery_first_slot + k` [M: black-box phase 2 analysis].
- **LFN broadcast schedule** (stage 4): the FHSS runs it from the FHSS activation (`ns_fhss_ws_lfn_bc_set()`: `bc_interval_ms`, the BSI of the border router's hopping schedule, as in its LBS-IE); every LPA and LPC carries an LBT-IE.
- **Sync frames** [M items 24, 32, 48, §5.2; S `wsbrd` `ws_mngt.c`]: only while the border router has an LFN child. In the slot of every sync period (slot number a multiple of `bc_sync_period`) an LTS, or a broadcast LPC during the first `maintain_parent_time` sync periods after the first child appears and after each LGTK event; an LGTK event's LPC goes in the next slot, whatever its number. The seconds timer queues the frame when its slot is less than 2 s away; the MAC holds it until the slot.
- **LTO-IE**: the offset the upper layer gives is the phase of the LFN's slots against the LFN broadcast slots; the FHSS converts it at TX time (`LFN_MAC.md` §2.2), so the LFN's unicast slots stay at least 300 ms from the broadcast slots.
- **Security**: frames to an LFN child (data through `ws_llc_lowpan_mpx_data_request()`, LPC) and the broadcast sync frames use the active LGTK (key index 5–7); everything else uses the GTKs as before (§8).
- **Registration**: the LFN's NS(ARO) is handled by the existing 6LoWPAN-ND code: a registered neighbour-cache entry, through which the border router routes to the LFN; a non-FFD child is published to RPL (`rpl_control_publish_host_address`), which for the root is local.
- **EARO (RFC 8505)** [S: RFC 8505, `wisun-br-linux` `nd_router_object.c`; M: item 19]: Silicon Labs' LFN registers with an NS from its link-local address, the address to register as Target, and an EARO with T and R set and a TID; then each RFC 9685 multicast group with P = 1. On a FAN 1.1 interface, such an NS registers the Target (the same checks as an ARO) and is always answered by an NA with an EARO echoing the flags and TID (the Wi-SUN omission of a successful NA does not apply); a multicast registration is accepted (status 0) and kept with its lifetime (lifetime 0 removes it); a parent allocates each registration and keeps at most `mc_reg_per_child` (16) per LFN child and `mc_reg_max` (2 048, about 80 kB) in all (`ws_lfn_settings_t`; the first version had a static table of 16, then 32: the scale tests showed it full with 10 LFNs of 3 groups each), and one that does not fit is refused with status 2 (Neighbor Cache Full, RFC 8505 §4.1), which the LFN reports and retries at its next refresh. A refusal keeps the LFN as a neighbour (Nanostack removed the neighbour after any negative NA, as for a failed address registration: the first test lost 5 of 9 LFN children that way), and the registrations of an LFN that is no longer a neighbour are freed (`ws_lfn_parent_child_removed()`, also checked when the table is full). Before, the 17th registration was answered with status 0 and not kept. Emulator `test_lfn_mc_full.sh` (9 LFNs under the border router, 6 groups each: 54 registrations, `lfn_mc_reg_max` 32), 6 seeds: 32 kept, 22 refused with status 2, each refusal reported by its LFN, no child removed. The group `ff15::810a:64d1` that every emulated LFN registered came from the emulator's demo multicast application (`multicast_helper.c`), which `wsnode` joined at start; LFNs no longer join it. The group's packets are copied to that LFN child (next point). **Our LFN registers its addresses with an EARO** (T and R set, a TID, the EUI-64 as ROVR; NS from its link-local address, `icmpv6_build_ns_earo()`), as Silicon Labs' LFN does, and its groups with an EARO (P = 1). The TID [S: RFC 8505 §5.2, §5.2.1] starts at 240 and is a lollipop counter incremented with each registration (and refresh); the release of an old parent is an EARO with lifetime 0 and the current TID. A router publishes an address registered with an EARO in its DAO with the TID as path sequence [S: RFC 9010 §6.1] (`rpl_control_publish_host_address_tid()`; the target keeps that sequence, without the router's own increments). At the root, a DAO for an external target from another router than the one it holds, with an older path sequence (RFC 8505 lollipop comparison), is stale: the router the host left, refreshing it; it is ignored (`rpl_downward.c`) [I]. Before, the root followed the last publisher, so an old parent that never got the LFN's release took the route back with its next DAO refresh (emulator `test_lfn_parent_gone.sh MODE=uplink`: the old parent no longer hears the LFN; 3 of 3 failed, one downlink and one echo lost about 1 100 s after the move). Limits: an RFC 6775 host (ARO, no TID) that moves to a router whose own counter for it is lower than the old router's is now ignored until the old path expires; Wi-SUN FAN 1.0 has no such hosts, and our LFNs and Silicon Labs' use EARO. A host that restarts with TID 240 under a new router, while the old router still publishes a newer TID, is ignored the same way.
- **Multicast** [M items 41–42; S: RFC 9685 §6 (the 6LR delivers the group's packets to the registered 6LN), RFC 7731 (MPL)]: a multicast leaving the parent is also sent as a MAC-unicast copy (IPv6 destination unchanged) in its window to every LFN child for `ff02::1` (`lowpan_down()` → `ws_lfn_parent_multicast_copy()`), and a packet of another group to the LFN children that registered it. A group packet carried by MPL (tunnelled to `ff03::fc`, or with an MPL option) is copied once, when MPL accepts it as a new message, received or seeded here (`mpl_forwarder_process_message()` → `ws_lfn_parent_mpl_copy()`), not on each MPL transmission: MPL sends a message again on Trickle expirations, or not at all when it has heard k copies, so a copy per transmission would give duplicates or none. The copy is the inner packet (tunnel removed); a hop-by-hop header holding only the MPL option is removed (an LFN is no MPL forwarder; the option type tells it to discard the packet), as `wsbrd` does [M item 41]. A router thus copies the border router's group packets to its LFN children.
- **Queues for LFN children** [I]. A packet to an LFN child waits in the parent's MAC for the LFN's next window, minutes with long listen intervals. Three Nanostack limits made that wait stall the parent: the 6LoWPAN adaptation layer allowed 10 unicast packets in the MAC at once (`LOWPAN_ACTIVE_UNICAST_ONGOING_MAX`), one per destination, and a fragmented packet blocked every other transmission until its last fragment; the LLC allowed 16 messages (`LLC_MESSAGE_QUEUE_LIST_SIZE_MAX`), and its 4-bit MPX transaction counter looped forever once 16 messages waited (found with 20 LFNs under one router). Now packets to LFN children have their own bounds: up to 4 per LFN and 64 in all in the adaptation layer (`LOWPAN_LFN_ACTIVE_PER_DST`, `LOWPAN_LFN_ACTIVE_MAX`), each fragmented one with its own fragment buffer so that it blocks nothing; up to 128 in the LLC (`LLC_LFN_MESSAGE_MAX`), outside the 16 and outside the transaction-ID uniqueness (the ID serves MPX reassembly at the receiver, which never mixes two of our frames to one LFN). The adaptation layer marks a packet with more to follow for the same LFN (another packet or fragment) so that the MAC sets the frame-pending bit (`LFN_MAC.md` §4). The MAC TTL (`tx_ttl_intervals`, 20 listen intervals) stays the only age limit for these packets.

## 8. LGTK

FAN 1.1 gives LFNs their own group keys, LGTKs, distinct from the GTKs of the FFNs. Our code is written from the public sources listed below, not copied: **[S]** `wisun-br-linux` v2.10.3 `common/specs/ws.h` (KDE types), `common/kde.c` (KDE layouts), `common/authenticator/authenticator_key.c` (which KDEs go to which role, quoting Wi-SUN FAN 1.1 6.5.2.2), and the Apache-2.0 stack files of `wisun-br-linux` v1.9.1 (`key_sec_prot.c`, `auth_fwh_sec_prot.c`, `auth_gkh_sec_prot.c`: the node role read from the key request); `examples/wsbrd.conf` (LGTK timer names and defaults); **[M]** the black-box results, items 48–51.

**KDEs** (`kde_helper.c`, Wi-SUN OUI `0c:5a:9e`): node role (type 3, one byte), LGTKL (type 4, one byte, bit i: LGTK i live), LGTK (type 5, the GTK KDE's layout: key index 0–2 in bits 0–1, a reserved byte, the key).

**Handshakes.** The supplicant's key request (initial EAPOL-Key) carries, for an LFN, its LGTKL and an NR KDE with role LFN, instead of its GTKL [S: `wsrd` writes GTKL, LGTKL and NR; the authenticator reads the NR KDE from the key request]. The LFN also puts its NR KDE in 4-way handshake message 2, in clear under the MIC; the authenticator only traces it, since it takes the role from the key request. The authenticator, on an NR KDE with role LFN, switches that supplicant's group keys to the LGTKs (`sec_prot_keys_lfn_set()`): the key to insert is chosen among the LGTKs by its LGTKL, and message 3 and group-key handshake message 1 carry an LGTK, its lifetime and the LGTKL instead of a GTK and the GTKL. A key request without an NR KDE (FAN 1.0, our FFNs) is handled as before; one with role LFN while the border router has no LGTKs is dropped [S]. The LFN reads LGTK and LGTKL KDEs where an FFN reads GTK and GTKL.

**Keys.** The border router keeps three LGTKs next to its GTKs (`pae_controller_t.lgtks`), in MAC key slots 4–6 with key indexes 5–7 (the emulated MAC's key table has 7 entries; a smaller table gives an error and no LGTK on the MAC). Their GAKs are derived from the network name like those of the GTKs. An LFN keeps its LGTKs in its group-key slots 0–2 with key indexes 5–7 (`ws_bootstrap_nw_key_set()`), so a key table of 4 is enough for it.

**Lifecycle on the border router** (`ws_pae_auth.c`, in the authenticator's second timer, once the interface parents LFNs):
- the first LGTK is generated and active at once;
- the next one is installed when the active one has used `lgtk_new_install_required` % of `lgtk_lifetime_s`, and activated `lgtk_lifetime_s` / `lgtk_new_activation_time` before the active one expires [S: LGTK_NEW_INSTALL_REQUIRED, LGTK_NEW_ACTIVATION_TIME];
- **[I] activation guard:** it is activated no sooner than `lgtk_activation_guard_s` after its installation. An LFN fetches a new LGTK about `lgtk_max_mismatch_s` after the LPC that shows its hash; a parent that switches earlier sends frames the LFN cannot read and LPCs it cannot decrypt (black-box item 51: `wsbrd`'s NA under key 7 was not acknowledged for 17 s). The default 300 s covers 120 s of mismatch wait, an LPC that missed its window and the next sync period (50 s), and the handshake. If the active LGTK expires first, the next one is activated then, whatever the guard;
- an LGTK whose lifetime ends is removed;
- `ws_management_lfn_lgtk_rotate()` installs the next LGTK now and shortens the active one's lifetime so that the activation falls when the guard has passed; the old LGTK then expires `lgtk_lifetime_s` / `lgtk_new_activation_time` later.

**Each LGTK event** (installed, activated, expired) increments the LFN version, updates the LGTK hash and active index for the LGTKHASH-IE (`ws_info->lfngtk`), and sets `lpc_pending`: a broadcast LPC goes in the next LFN broadcast slot, and the sync frames of the next `maintain_parent_time` sync periods are LPCs [M item 48: one event, one version, an extra LPC]. The LPC is secured with the active LGTK (`ws_lfn_lgtk_security_set()`), as are data frames to LFN children (`ws_lfn_parent_tx_key_index()`, from the LLC). FAN 1.1 PAN configurations carry the same LFN version and LGTK hash, as before.

**On the LFN** (`ws_lfn_parent.c`, `ws_pae_supp.c`): each LPC's LGTK hash is applied before its key index (`ws_pae_controller_lgtk_hash_update()`): LGTKs it no longer lists, or whose hash differs, are removed; listed ones become fresh; a listed LGTK the LFN lacks starts a timer of `lgtk_max_mismatch_s`. When it ends, the LFN sends a key request to its parent (`ws_pae_supp_lgtk_key_request()`), and the parent answers with a group-key handshake; retries are an FFN's key-update retries. A later LPC whose hash matches stops the timer [M items 49–50; I: a fixed delay from the first LPC that shows the new hash; Silicon Labs' two samples, 113 and 117 s, cannot tell a fixed delay from a random one]. The LPC key index then sets the active LGTK. The LFN's EAPOL target after the join is its LFN parent, not an RPL parent.

**Deviations [I].** The LFN keeps its 5 s interval during the group-key handshake (Silicon Labs' LFN listens every 1.25 s then, item 50); the handshake's first message then waits for the next window. The key request is sent once the timer ends, without the random spread an FFN uses after a GTK mismatch.

**Storage and frame counters** (with a file system given by the application):
- the border router stores its LGTKs, the LFN version and the LGTKs' MAC frame counters (`pae_lgtks`, `ws_pae_auth.c`) and restores them at start, the counters `FRAME_COUNTER_INCREMENT` (1 000 000) higher: its LFNs keep their group key across its restart;
- an LFN keeps its LGTKs in its group-key slots 0–2, so the supplicant's GTK storage and the GTK frame-counter store hold them: after a reset it installs its stored keys (no EAP-TLS) and restarts its counters 1 000 000 above the stored ones;
- an FFN router that parents LFNs stores its LGTKs' MAC frame counters with the LGTK they belong to (`pae_lgtk_fc`, `ws_pae_controller.c`): when it installs an LGTK it finds there (after a reset, or an LGTK removed and fetched again), the MAC counter starts 1 000 000 above the stored one. Each counter is stored when the LGTK is installed, when it has advanced by `FRAME_COUNTER_STORE_THRESHOLD` (994 999, checked every 60 s) and when the interface stops, as for the GTKs, so a counter value is never used twice under one LGTK as long as a router sends fewer than 994 999 frames per minute under it. Before, a router that restarted and fetched the same LGTK started at 0: its LFN children dropped its frames as replays (11–12 `MLME_COUNTER_ERROR` per run in `test_lfn_reset.sh`, the LFN's LPCS unanswered until it dropped its keys and authenticated again) and CCM* nonces were reused.

**Revocation, frame-counter lifetime, LFN key lifetimes** (phase B6) [S: Wi-SUN FAN 1.1 6.5.2.5 as quoted in `wisun-br-linux` v2.10.3 `authenticator.c` `auth_revoke_gtks()`; `examples/wsbrd.conf` `lfn_revocation_lifetime_reduction`, `lpmk_lifetime`, `lptk_lifetime`; the Arm stack's GTK frame-counter check `ws_pae_auth_lifetime_key_frame_cnt_check()`]:
- **Revocation of node access** (`ws_bbr_node_access_revoke_start()`, after `ws_bbr_node_keys_remove()` of the node) now treats the LGTKs as the GTKs: with R = `lgtk_lifetime_s` / `lgtk_revocation_reduction` (30), if the active LGTK has more than R left, the other LGTKs are removed and the active one gets R; otherwise all but the active and the next one are removed and the next one gets R; then a new LGTK is installed with the normal lifetime. Each step is an LGTK event (LFN version, hash, LPCs). The new LGTK becomes active at the end of R whatever the activation guard. A revoked node must be kept out by its credentials as well (a valid certificate lets it authenticate again).
- **Lifetime by frame counter**: once an hour the border router compares the share of the active LGTK's frame counter space left with the share of its lifetime left; when the counter goes faster (and over 20 % is used), the lifetime is cut to the counter's share, so that the next LGTK is installed and activated before the counter runs out.
- **Reception after an expiry**: when the active LGTK expires and the next one is activated at that moment (a revocation, or a guard longer than the time left), the old LGTK stays installed one sync period + 60 s more, so that the LFNs' uplinks under it, until the next LPC tells them the new active index, are still received (first `test_lfn_revoke.sh` runs: 1 uplink of 27 lost in 1 of 6 seeds).
- **Role-based PMK and PTK lifetimes**: a supplicant that authenticates as an LFN (NR KDE) gets `lpmk_lifetime_s` (788 400 min, 18 months) and `lptk_lifetime_s` (525 600 min, 12 months), the FFNs keep theirs (4 and 2 months); the LFN uses the same values for its own keys.

Checked: emulator `test_lfn_revoke.sh` (border router and two LFNs, LGTK lifetime 3 600 s, LFN 2 revoked at 600 s), 6 of 6 seeds pass (LFN PMK and PTK lifetimes, the cut to 120 s and the new LGTK at the revocation, activation 120 s later, LFN 1 holding the new LGTK before, LFN 2 back through EAP-TLS, LFN 1's traffic complete); `test_lfn_join.sh` with the active LGTK's counter set to 95 % used at 300 s (`test_lgtk_fc_at_s`, `test_lgtk_fc`): at the hourly check (3 601 s) the lifetime went from 7 772 401 s to 311 040 s (4 % left) and the next LGTK was installed at once; the LFN fetched it 129 s later.

**Limits.** With a guard longer than the time between installation and expiry, activation happens at the old LGTK's expiry; the LFN's uplinks under the old key then fail until it hears the next LPC (seen with 6-minute lifetimes: 3 losses in 62 request-echo exchanges).

**Results** (emulator `test_lfn_join.sh`, same conditions as §7):

## 9. FFN routers as LFN parents (stage 5)

**Parents.** `ws_management_lfn_parent_set(id, true)` is accepted on a FAN 1.1 router as on the border router (emulator: `enable_lfn = true` in `wsnode`'s configuration). A router parents LFNs once it is operational (`ER_BOOTSTRAP_DONE`) and holds an LGTK: until then it ignores LPAS and LPCS and sends no sync frames. It then runs the same parent code as the border router (`ws_lfn_parent.c`): its own LFN broadcast schedule (the network's BSI, which the FHSS takes from its configuration once the router has learned it), LTS and broadcast LPCs while it has an LFN child, LPA and LPC answers, unicast frames held for the LFN's windows. Its seconds timer runs every second while it parents LFNs (`ws_bootstrap_ffn_seconds_timer_next()`).

**LGTKs for a router** [S: `wsrd` sends GTKL, LGTKL and an NR KDE; `authenticator_key.c`: an FFN gets GTKs and LGTKs]. A router that parents LFNs sends a key request with its GTKL, its LGTKL and an NR KDE with the router role (`sec_prot_keys_t.ffn_lgtk`). The border router answers as before for the GTKs (EAP-TLS, 4-way handshake, group-key handshakes), then sends each LGTK the router lacks in a group-key handshake of its own [I: FAN 1.1 allows both in one message]. One handshake carries one set: `sec_prot_keys_lgtk_mode_set()` selects the set for each, and the KDE code reads and writes LGTK and LGTKL KDEs for it as for an LFN. The router puts its LGTKs on the MAC at key indexes 5–7 (`ws_pae_controller_ffn_lgtk_install()`), and follows the LFN version and LGTK hash of the border router's PAN configurations: a hash it does not match starts a key request at once [I: the border router activates a new LGTK `lgtk_activation_guard_s` after installing it, and the router's children fetch it through the router, so the GTK update trickle, minutes long, is too slow], and each new LFN version gives its children a broadcast LPC. It secures its LFN frames with the active LGTK once it holds it, until then with the one it used last.

**Discovery and choice** (`LFN_MAC.md` §2.4). The LPAS sweep covers the channels of the plan (as an FFN's PAN advertisement solicit), and its LND-IE gives the discovery window: `lnd_response_delay_ms` after the sweep starts (and after the sweep's end, at about 20 ms per channel), `lnd_slots` × `lnd_slot_time_ms` long (40 × 60 ms, [M item 4]). Each parent sends its LPA in a random slot of it, a quarter into the slot [S: `wsbrd`]. The LFN keeps up to four LPAs and, after the window, chooses the parent with the lowest routing cost (PAN-IE) among those heard `CAND_PARENT_THRESHOLD` (10 dB) above its minimum sensitivity, the strongest on a tie; without one, the same among those above the minimum [I: an FFN's candidate-parent margin]. An LPA heard outside a discovery window is taken at once, as before. A parent counts an LFN that sent it an LPAS as a candidate child for 600 s; the LFN's LPCS and its secured frames make it a child for twice its registration lifetime [I].

**Through the router.** EAPOL: the LFN's authenticator target is its parent, and the router relays as for an FFN joiner. DHCPv6: through the router's relay. Registration: the LFN's NS with ARO to the router; the router publishes the address to RPL (DAO target) and the border router routes to the LFN through it. The route exists once RPL's DAO delay has passed (1–7 s in the runs below), so a downlink in the first seconds after the LFN's registration can be lost. Multicast: a router copies the `ff02::1` multicasts it sends to its LFN children; the border router's `ff02::1` does not reach LFNs under a router (link-local). A group of realm-local scope or wider reaches them through MPL: the router copies each new MPL message of a group to the LFN children that registered it (§4), also when Trickle suppresses its own retransmission.

**Router fixes found with the multicast tests.**
- An LFN parent that lacks the active LGTK asks again at each PAN configuration with the same LFN version (`ws_bootstrap_ffn.c`) [I]. Before, it asked only when the LFN version changed: in 1 run of 10, the border router's group-key handshake message 1 with the LGTK was lost, its retries came after the router's authentication had ended and were refused ("Incoming KMP rejected, auth not ongoing"), and the router never parented LFNs.
- On the kits, a router rebooted with its keys from flash (`FW_FLASH_FS`) while the border router had new LGTKs (at the time the border router did not store them; it does since d66a796) never fetched the LGTK: its key request went out before it had an RPL parent (no EAPOL target), failed, and armed the retry timer anyway, and later requests were blocked by that timer and by the GTK update trickle. Now a failed request arms no timer (the next PAN configuration tries again), and an LGTK key request replaces a GTK update still waiting on its trickle (the request carries the GTKL, so the border router sends the missing GTKs too) [I]. With both, the router got its LGTK 12 s after its join.
- A router's key request answered by a full EAP-TLS (the border router no longer held its PMK; FG25 kits, a cold start with keys in flash: LGTK 521 s after the router's reset). Two faults in the supplicant [I], reproduced in the emulator (`test_lfn_keyreq.sh`: the border router forgets the router's PMK and PTK and installs a new LGTK, the router restarts with its key storage, the link is dead around the request): (1) the end of the router's bootstrap removes the supplicant's EAPOL target (`ws_pae_controller_bootstrap_done()`), and an EAP-TLS that came after it was refused ("Incoming KMP rejected, auth not ongoing" at 721, 832, 917 and 1 051 s, LGTK at 1 134 s, as on the kits); it is now accepted while the key request is on its way, the sender becoming the target again (LGTK at 722 s); (2) a request not acknowledged at the MAC waited for its retry timer (180–420 s; LGTK at 1 071 s); the next LGTK hash mismatch now sends it again (LGTK at 673 s, 9.5 s after the link's return).
- A router's LPA carries its routing cost now (`ws_bootstrap_routing_cost_update()`): the PAN-IE value was updated only when the router sent a PAN advertisement, which can be rare, so LPAs carried a stale cost (often its parent's, 0).

**Better parent while attached** [I, from the sources given]. The LFN of §1–§8 kept its parent as long as sync frames came and uplinks got through. Now, while attached, it runs a background check: an LPAS sweep and a short discovery window (`parent_check_lnd_slots`, 10 slots: 0.6 s) while it keeps its parent, the mechanism of the parent change without loss (above). Timing: 0.5–1.5 × `parent_check_s` (6 h) after the last check, or × `parent_check_weak_s` (1 h) while the parent's link is weak, the next check being brought forward when the link becomes weak; the random spread keeps LFNs that joined together from sweeping together. A parent's link is weak when the EWMA of its RSL (sync frames and LPAs, smoothing 1/8 as Wi-SUN's RSL EWMA) is below `DEVICE_MIN_SENS` + `CAND_PARENT_THRESHOLD` (10 dB) [S: Wi-SUN FAN candidate parent set, Nanostack `ws_common_defines.h`, `ws_bootstrap.c`].

At the end of the window the best candidate (the join rule: good link first, then routing cost, then RSL) replaces the parent only if it is better with hysteresis (`ws_lfn_better()`):
- the parent's link is weak: the candidate's RSL is `CAND_PARENT_HYSTERISIS` (3 dB) above the threshold [S: the Wi-SUN candidate-parent hysteresis], or 2 × 3 dB above the parent's;
- both links are good: the candidate's routing cost is lower by `parent_switch_cost` (192, RFC 6719 MRHOF `PARENT_SWITCH_THRESHOLD`) [S];
- a good parent never gives way to a weak candidate.

A candidate's LPA is checked first (network name, UTT, BT, PANID, FLUS + LCP or US, BS, a valid channel plan and function: `ws_lfn_lpa_valid()`), in a background check and in a parent search alike: an unusable one leaves the parent in place. Before, the change cleared the parent and stopped the broadcast windows, then `ws_lfn_lpa_analyse()` refused the LPA, and the LFN stayed operational with no parent and nothing to recover it. If the change still fails after the parent was dropped (no neighbour entry for the new one), the LFN starts a discovery again, keys kept. Emulator: `test_lfn_better.sh EXPECT=stay OLD_RSSI=-87 NEW_RSSI=-60 ROUTER2_EXTRA="-o test_lfn_lpa_unusable=1"` (router 2 is better but its LPAs lack the BS-IE, `ws_test_lfn_lpa_unusable()`), 6 seeds: router 1 kept through 3–5 checks, 21 unusable LPAs refused, every request echoed.

Otherwise the LFN keeps its parent and applies the parent's own LPA (its UTT and BT; an LTO-IE if the parent sent one). A parent sends no LTO-IE to an LFN that is already its child [I]: the LFN's slots stay where they are on both sides, whether or not the LPA and its ACK get through (with an LTO-IE, a lost ACK left the parent and the LFN with different slots, and downlinks failed until the LFN's next uplink).

The switch: no EAPOL (keys kept), LPCS → LPC → ARO and group EARO to the new parent, whose DAO moves the route. The old parent may still hold frames for the LFN in its old windows, so the LFN sends it an NS at once (any frame carries the LFN's new timing, LUTT and LUS-IE); `parent_release_s` (15 s) plus two listen intervals after the new registration, once the new route has reached the border router and the old parent has had two of the LFN's windows to deliver what it still held, it releases the old parent: NS with ARO lifetime 0 for its address and EARO lifetime 0 for its groups [S: RFC 6775 §6.5.3, RFC 8505 §5.1: lifetime 0 deregisters]. A successful ARO gets no NA in Wi-SUN (Nanostack omits it and takes the MAC ACK as the answer), so the LFN counts the MAC ACKs of these NS and sends them again every 10 s until each was acknowledged, 4 tries in all (`WS_LFN_RELEASE_TRIES`); before, one lost NS left the old parent publishing the address, and its DAO refreshes took the route back [I]. These NS are routed on-link to the old parent (`icmpv6_build_ns()` routes before setting the interface, so a link-local destination took the default route through the new parent). The old parent drops the registration and its DAO target and its copies to the LFN, stops its sync frames to it, and keeps the LFN as a neighbour for 60 s, or two of its listen intervals + 10 s if longer (`ws_lfn_parent_child_release()`), to deliver frames still queued for it; the LFN's last frames (the deregistrations) do not keep it a child. Before, the LLC removed a neighbour with a lifetime under 240 s at the next data confirm to it ("temporary entry"), which purged the frames still queued for the LFN: in `test_lfn_better.sh` seed 3, a downlink that router 1 held (its first try collided in the LFN's window with a frame from router 2, which router 1 cannot hear) was purged at the release. LFN children are now excluded from that rule.

At the border router (RPL root, non-storing), a DAO target published by the routers of a leaf (external target) now follows the router that published it last: a DAO from another router for the same target replaces its transits even with the same path sequence (`rpl_downward.c`, the DAO source kept per target) [I; S: RFC 9010 gives the 6LR's DAO the registration's TID as path sequence for this]. Before, both routers published the LFN's address with the initial sequence 240, the root kept both transits and went on routing through the old router, which had no route to the LFN any more. FAN 1.0 targets (routers' own addresses, not external) are unchanged.

Power: in the emulator (FG25 profile, EU mode 3, +10 dBm, one LFN under the border router, idle, 3 seeds × 3 600 s with a check every 300 s against none), a check costs 11.8 mC: 0.6 s of RX (the window), 0.17 s of TX (the LPAS sweep), the MCU awake meanwhile (64.0–67.9 µA against 24.5–25.1 µA). With the defaults that is 0.55 µA on average while the parent's link is good (one check per 6 h: 0.1 s RX and 0.03 s TX per hour) and 3.3 µA while it is weak (one per hour: 0.6 s RX, 0.17 s TX per hour). The parents that answer count the LFN as a candidate child for 600 s and send it sync frames meanwhile (FFN energy, as after a join's discovery).

Detection: an FFN hears an LPAS only on the channel it listens on, and it may be on its broadcast channel or hop away during a sweep. With one sweep per check, a check heard a router in range in 72 % (router 2) and 81 % (router 1) of 137 checks (`test_lfn_better.sh EXPECT=stay`, `DUR=7200`, 6 seeds); with two sweeps back to back (`parent_check_sweeps` 2, the window opening after both), 94 % of 140 checks for each router. A better parent is thus found after 1.06 checks on average: with the defaults, typically within 6–9 h while the parent's link is good and 1–1.5 h while it is weak. Cost of the second sweep (same power profile, a check every 300 s, 3 seeds × 3 600 s): 64.0–64.3 µA with one sweep, 86.7–87.1 µA with two, 24.5–24.9 µA without checks, so a check costs 18.6 mC instead of 11.8 mC (TX doubles). With the default intervals: 0.86 µA instead of 0.55 µA while the parent's link is good (+0.31 µA), 5.2 µA instead of 3.3 µA while it is weak (+1.9 µA).

## 10. On the FG25 kits (stage 6)

The firmware (`nanostack-efr32fg25-freertos`) builds the router program as an LFN (`wisun_lfn`) and the border router with LFN parenting (`FW_LFN_PARENT`); its README has the build, the board-specific parts and the measurements.

**Memory errors found on the way.** The first LFN image faulted during EAPOL on the kit (an unaligned access in SHA-1, then a bus fault in the MAC's IE copy). Both were heap corruption, which the emulator did not show; the in-process programs built with AddressSanitizer (`-fsanitize=address`) found two errors:
- `supp_fwh_sec_prot.c` (stage 3 code): the LFN's NR KDE in 4-way handshake message 2 was given both to `eapol_pdu_key_frame_init()` and to `sec_prot_lib_message_build()`, which copied it a second time, 7 bytes past the frame buffer. The frame sent was correct; the heap after it was not.
- `dhcp_service_api.c` (inherited from Nanostack): the DHCPv6 relay's I/O vector was declared inside a block and used by `socket_sendmsg()` after it. FFN routers relay DHCPv6 too; with `-Os` on a target the stack slot can be reused.

With both fixed, the LFN tests (one LFN with an LGTK rotation through a router, the six-LFN mesh, one LFN under the border router) and FAN 1.0 `dag_simple` (600 s) run clean under AddressSanitizer, and FAN 1.0 `dag_simple` logs are byte-identical to `b1b9cc5`.

**An LFN under a router on the kits** (the firmware README, "An LFN under a router on the kits"). Border router – router (`FW_RN_LFN_PARENT`) – LFN, with a test-only MAC filter in the LFN so that it hears only the router: the router gets its LGTK, the LFN joins through it (EAPOL and DHCPv6 relayed, address registered, routed by the border router) and answers the border router's pings, as in the emulator's `MESH=1`. Its idle current is 23.8–24.8 µA (24.9–26.9 µA under the border router).

**Rejoin after the network restarted.** An LFN that loses its parent rejoins without EAPOL while its keys are valid (black-box item 47). After a restart of the border router (new PAN ID, new GTKs and LGTKs) it kept rejoining with its old keys: its LPCS, secured with the old LGTK, got no LPC, and it lost the parent again after 375 s, without end. Two rules now end this [I]:
- keys belong to a PAN, as for an FFN (`ws_pae_supp_nw_keys_valid_check()`): an LPA from another PAN ID drops them, and the LFN starts its discovery again, with EAPOL;
- after `WS_LFN_LPCS_MAX` (4) LPCS without an LPC, the LFN drops its keys and starts its discovery again (a restarted network with the same PAN ID, or a parent that lost them).
The parent-loss test (`SILENT_AT=300`, no traffic, 3 seeds) still rejoins without EAPOL; FAN 1.0 `dag_simple` logs are unchanged.

A lower floor saves more but leaves less margin for a crystal whose frequency moves with temperature between two syncs; the floor is a setting. Two errors showed once the windows were narrow, both fixed: the LFN's own interval on its clock was rounded to the µs (a 5 s interval at 15.6 ppm lost 0.9 µs a slot: 5–9 ms in 14 h, and test_lfn_silence's 10 h downlink missed the window), and each sync moved the LFN's own slots by the parent's broadcast interval's rounding; the interval now runs to the ns and the sync error is measured from the last sync's slot start at the exact rate. The widening also uses the extended clock, so a sync older than 2^30 µs (Eco) no longer means the maximum widening.

**Bugs found and fixed by these runs** (all LFN or LFN-parent paths; FAN 1.0 unchanged):
- 32-bit clock with a 10 h sync period (`LFN_MAC.md` §2.3): the rate was never measured (sync periods beyond 2^30 µs), the widening wrapped after 71.6 min, `bc_sync_only` armed its window at a wrapped time, uplinks after more than 71.6 min without a frame from the parent went to a wrong channel, and a sync moved the LFN's slots by the whole 10 h error although the parent's view of them dated from the last uplink (downlinks then missed the LFN).
- 6LoWPAN adaptation layer: a second packet to an LFN within one listen interval was dropped after 30 s in the queue (`LOWPAN_TX_BUFFER_AGE_LIMIT_LOW_PRIORITY`): with 60–300 s intervals every second packet was lost. The MAC's LFN TTL applies instead.
- A router whose LGTK handshake was lost at the join, and whose key request came while its authentication was still on its way, never got an LGTK and never parented its LFN (§9; Balanced seed 4).
- The parent search started exactly two sync periods after the last sync frame, so with one late sync frame it took the radio just before the next one; it now waits one LFN broadcast interval more.

**Long listen intervals end to end** (phase B1, completed). Eco with a 4 h unicast interval (`lfn_listen_interval_ms=14400000`), 10 h sync period, 72 h, before these fixes: 3 of 9 uplinks arrived, 3 of 6 sync periods missed, the LFN under the router never operational, and `widening_max_us` had to be raised to 1.8 s by hand. The causes, all fixed:
- The LFN's parent entry expired after 2 200 s without a frame from the parent, and every uplink was then refused at the adaptation layer (§3, "Neighbours"). It caused the router case (the parent's entry gone before the LPC came) and most lost uplinks.
- The join waited one 4 h interval for the LPC and another for the DHCPv6 reply; the NA wait (300 s) expired before the NA could come in the next window, so the LFN registered twice and searched for a parent each time. The join interval is now kept until the first registration (§3), and the NA wait counts one listen interval more (§5).
- Once the rate was measured, the LFN's own slots moved by about 0.36 s at the next sync: the sync's phase error scaled by the time since the last LUTT-IE (the way before the rate is known), plus the interval at the new rate applied from an anchor that was not the parent's reference. The LUTT-IE offset was also read by the parent in its own µs while we wrote ours (20 ppm × 3 h = 0.2 s). The LFN now writes the offset in the parent's µs once the rate is known, keeps the parent's view of its slots as it gave it (last LUTT-IE, or the last LTO-IE applied) and, at each sync with the rate known, sets its own slots from that view at the measured rate, to the ns (`LFN_MAC.md` §2.3).
- Uplinks: a parent router's FFN unicast and broadcast hopping follow the border router's time base (FAN 1.0 drift compensation), while its LFN broadcast schedule, from which the LFN measures its rate, runs on the router's own clock. With 4 h between the parent's UTT-IEs the LFN predicted the router's channel 0.4 s off. The LFN now measures the rate of the parent's FFN schedules from its UTT-IEs (ACKs, downlinks, LPAs; over at least 10 min, `LFN_MAC.md` §2.3).
- The fixed 100 ms widening bound: now automatic from the sync period and the interval (§5).
- A sync frame or an LFN window lost to the parent's own asynchronous sweep (below).

Result (`test_lfn_profiles.sh`, Eco, 4 h interval, `BR_PERIOD=18500 LFN_PERIOD=27000 DUR=259200`, 3 seeds × 72 h): every check passes in each seed: operational at 213–614 s under the router and 329–484 s under the border router; 14 of 14 downlinks and 10 of 10 uplinks per LFN, all echoed; `ff02::1` 14 of 14; 8 sync frames, no sync period without one; phase error at most 32 µs from the third sync. LFN current from 24 h: 6.0–6.3 µA (the 300 s Eco interval: 10.8–11.4 µA).

**Cost of the automatic widening bound, and the measured EM2 floor** (`test_lfn_profiles.sh`, 3 seeds each, the emulator's `efr32fg25-soc.ini` with the EM2 floor measured on our LFN, 7.0 µA instead of the datasheet's 4.6, and the LFN-only profile `efr32fg25-lfn.ini` with the RX plateau, TX, EM2 wake and teardown measured on our LFN):

The 7.0 µA floor adds 2.4 µA everywhere (Balanced was 9.1–10.0 µA, Eco 10.8–11.4 µA, §11 above). With Eco the automatic bound costs about 1 µA once the rate is measured (`drift_floor_ppb` 5 ppm × 10 h = 180 ms each side, which the 100 ms bound cut), and much more before: the rate needs two sync frames, 10 h apart, and until then the windows widen at `drift_ppm` (50 ppm) up to 1.8 s each side (the first 20 h average 23 µA). A lower `drift_ppm` for a better crystal, or a lower `drift_floor_ppb`, reduces both; a fixed `widening_max_us` keeps the former figures but misses the windows of long intervals.

**A parent's asynchronous sweeps and its LFN children** (`mcast_eco` seed 1, `mcast_balanced` seed 1, the 4 h runs). A parent's PAN advertisement or PAN configuration sweep holds its radio for 0.3–0.6 s (one frame per channel); a frame waiting for an LFN window or an LFN broadcast slot in that time went one interval later (Eco: 300 s; the sync slot of a 10 h sync period: 20 h). `mcast_balanced` seed 1 missed Q 78 that way: the border router's PAN configuration sweep started at 7 097.70 s, LFN 2's window opened at 7 097.90 s with the radio busy ("rf rx lost: radio off" on the LFN for the sweep's frames), and Q 78 came one 60 s interval later, after the end of the counted traffic (reproduced on stack 7dfc4fe with the scripts of that time). In the MAC an asynchronous sweep now waits while a frame queued for an LFN (its window, an LFN broadcast slot, an LPA at its time) would be due before the sweep could end (channels × airtime + 3 ms each + 20 ms), at most 10 s; the LFN frame goes first and the queue is read again at its confirmation (`mcps_async_lfn_conflict()`, FHSS `lfn_tx_delay`). `wisun-br-linux` leaves frame timing to its RCP and has no such rule we could take [S: v2.10.3 `ws_mngt.c`, `ws_llc.c`]. With it, Q 78 comes in the next window (7 105 s), and the `mcast` tests pass under Balanced and Eco (full suite).

**Unit tests of these fixes.** `tests/fhss_lfn` (`test_own_ref`, `test_ffn_rate`, `test_tx_delay`) and `tests/lfn_units` (`test_async_hold`, `test_duplicates`, `test_lfn_ttl`). Built against stack 7dfc4fe (before the fixes; `OLD_STACK`), these fail: the own slots 224 ms from the parent's view (tolerance 0.5 ms), the parent's FFN reference 399 UFSI units off after 4 h (tolerance 6), a retry one listen interval later accepted, a new frame with the same sequence number dropped (twice), an expired frame to an LFN sent again. `test_tx_delay` and `test_async_hold` test code that did not exist then.

**Lost NAs** (tests agent's `test_lfn_lost.sh`). Three stack faults:
- A frame to an LFN that reached the MAC's TTL was put back in the adaptation layer's queue and sent again with a new sequence number, for ever: the lost NA always came at last, so the NA wait never expired under Balanced (the NA came at the TTL, 20 intervals, before the 60 min wait). The MAC's TTL is now final for LFN destinations.
- After a search for lost NAs that kept the parent ("no parent heard, parent kept"), the LFN never registered again: it does now.
- That search sent one LPAS sweep, which the border router missed while it hopped from a channel already passed to another (a 36-channel sweep takes about 0.35 s, a dwell 255 ms). A search while the parent is kept now sends `parent_check_sweeps` sweeps, as a better-parent check.

The release test with all four tries lost (`lost_release_all`) passes in seed 2 and fails in seed 1 on the test's timing: the link comes back at 728.5 s, 9.5 s after the fourth try, while that try's MAC retries and restarts still run (the last at 728.6 s), so the fourth try is acknowledged. In these runs the border router's "Ignoring stale path" path is not reached: the old parent sends one DAO after the move, for its own address; it re-advertises the LFN's address only at that target's refresh, hours later with the 36 h registration lifetime. A run with a registration lifetime of a few minutes would exercise it.
